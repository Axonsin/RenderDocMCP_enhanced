# 管线分析方法

## 1. 推荐的工具组合次序

以下次序是经验路径，不是硬性规定；每一步的工具名以实际发现的 MCP schema 为准。
原则：每一步缩小一点范围，避免一开始就拉全量明细。

```text
健康核对
  → 帧统计（总数、marker 列表）
  → action 树（marker_filter / exclude_markers / flags 过滤，锁定功能 Pass）
  → 选定 action：管线总览 → 阶段状态 → 绑定详情（binding_id 令牌链）
  → 输入/输出纹理列表（按方向与阶段过滤）
  → 资源追踪：整帧 usage（带 Timeline 分类）→ 单 action 依赖追溯
  → marker 子树汇总（把一个 Pass 当整体看负载）
```

过滤建议：排除已知噪声 marker（引擎 UI、调试链），但**排除列表本身要记录**——
它属于分析前提，换捕获要复核。

## 2. 区分三类节点

| 类型 | 识别特征 | 分析处理 |
|---|---|---|
| 真实操作 | 有几何/派发负载、绑定随内容变化 | 管线细读与资源追踪的主体 |
| 自动 marker | 引擎/中间件批量插入（UI 链、调试层、入场特效） | 默认折叠；用户问 UI 时才展开 |
| 功能 Pass | 同名多次出现（多相机、多光源级联） | 按实例区分，不得合并陈述 |

同名 marker 不等于同一功能；用子树内的 draw 数、绑定差异、输出目标来区分实例。

## 3. 资源追踪的四个要点

1. **版本与子资源**：同一资源名的不同 mip/slice/层可能在不同 Pass 写入；使用记录要
   带子资源维度。渲染目标、UAV、深度缓冲分别追踪。
2. **部分写入**：一次 Pass 可能只写纹理的一部分（视口裁剪、mask、逐 mip 生成）；
   "该 Pass 写过它"不等于"它整体来自该 Pass"。
3. **生产者判定**：对每个关心的资源，沿使用追踪找**全部**写入，再按执行顺序与采样
   关系确定最终内容来源。常见反例：后处理链中最近绑定者只是传递者；阴影图的生产者
   在阴影 Pass 而不在采样它的光照 Pass。
4. **混合依赖**：读写同帧发生（如 UAV 曲面细分、粒子更新）时，顺序与栅栏语义要单独
   说明，不能简化成先写后读。

## 4. 状态类查询的注意事项

- 管线快照是"该 action 执行时刻"的状态；比较两个 action 时用 diff 类工具对齐语义，
  手工对比两张快照容易漏掉中间被替换的绑定。
- 网格/计时类查询可能移动回放位置；长序列查询后重新定位到目标事件再继续。
- 需要修改观察点（如临时替换 Shader 验证分支）时，遵循证据契约 §3：记录起始状态、
  只撤销自己的替换。

## 5. 产出模板

报告主体建议三段式：

1. **帧结构**：Pass 列表（名称、范围、负载摘要、输出目标），自动 marker 单独列出。
2. **数据流**：按"几何 → 中间缓冲 → 后处理 → 最终输出"描述主链路；分支与可选
   Pass 注明触发条件。
3. **资源时间线**：每个追踪资源一行——生产者、消费者、子资源范围、读写类型。

管线图（结构化 JSON 或渲染 PNG）：节点 = Pass/关键 Draw，边 = 资源流；边上标注
资源名与读写方向。图中不画没有证据支撑的连接；推断边用虚线/标注区分。
