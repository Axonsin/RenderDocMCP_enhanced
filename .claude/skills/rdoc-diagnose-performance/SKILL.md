# RenderDoc 单帧性能诊断

产出**可证伪的优化假设**：每条带证据、适用条件、预期收益与反证检查——而不是
"建议减少 Draw Call"这类不可操作的泛泛之谈。

## 触发边界

适用：耗时归因（哪个 Pass/Draw 最贵）、瓶颈类别判断（填充率/带宽/几何/状态）、
可疑冗余（重复采样、过绘制、多余清屏）、GPU 计时解读。
不适用：

- 实施优化（改 Shader/工程代码）：遵循当前授权——用户已要求实施就直接继续，
  仅在缺少授权时先给出方案与 A/B 计划并询问；
- 单帧无法证明的问题：缓存命中率、跨帧加载、CPU 侧瓶颈——如实声明边界，
  不编造结论；
- 帧内容讲解 → 管线分析 Skill。

## 工作步骤

1. **健康核对与计时可用性（固定第一步）**：按 `references/tool-usage.md` §2 核对；
   随后确认 GPU 计时是否可用（计时接口的 available 标志）。不可用时明确告知并降级为
   基于绑定/负载结构的推断（全部标注 `inferred`），不假装有计时结论。
   **回放设备不同的计时不可以互相比较。**
2. **确定范围与指标**：确认分析范围（整帧/某 Pass）与用户关心的指标（帧时间、某
   Pass 耗时、显存带宽）。写入 `context.json`。
3. **耗时分布**：拉取全帧或范围内的 action 计时，排序找出头部贡献者；结合 marker
   层级把耗时归组到功能 Pass，而不是孤立看单个 draw。
4. **瓶颈类别证据**：对头部 Pass 逐类取证（方法见
   `references/performance-method.md`）——过绘制（同一像素被多个 draw 覆盖）、
   采样冗余（同一纹理被反复绑定/采样）、带宽（大目标读写、格式浪费）、几何负载
   （顶点数 vs 实际覆盖）、状态冗余（无变化的重复绑定/清屏）。
5. **区分四个概念**：绑定 ≠ 实际采样；有计时 ≠ 收益可迁移；单帧测量 ≠ 跨帧机制；
   相关差异 ≠ 因果。每条假设注明它属于哪一层证据。
6. **反证检查**：对每条假设主动找反例——如果假设成立，哪些测量应该不同？用现有数据
   验证；无法验证的写明需要什么额外测量（如 A/B 对照）。
7. **产出与实施**：按优先级排序的假设清单（证据、适用条件、预期收益与不确定性、
   建议的验证方式）。已在授权范围内（用户已要求实施）则继续实施并做 A/B 实测，实测
   结果如实报告；缺少授权时给出 A/B 方案后询问一次。允许结论是"证据不足"。

## 硬性约束

- 计时不可用、样本不足（如只有单帧单次回放）时，明确声明置信度，不宣称瓶颈结论。
- 不把"资源被绑定"当成"资源是瓶颈"；不把耗时排序直接当成优化收益排序。
- 收益预测有依据时给区间并标注不确定性来源；没有依据就写"待测"并附验证方法，
  不硬造数字。实施遵循当前授权，不重复确认已明确同意的事。

## 验收标准

- 头部耗时者有计时证据；每条假设有可证伪的表述与反证检查记录；
- 明确区分：实测 / 推断 / 需要额外测量才能判断；
- 给出优先级排序；预期收益有依据时给区间，无依据的条目写"待测"并附验证方法；
  列出"本单帧分析无法回答的问题"清单。
