# 故障树与已知失败模式

## 1. 故障分类树

```text
健康核对异常?
├─ 是 ──► 环境类：进程/驱动/设备/版本（见 §2）
└─ 否 ──► 业务查询异常
          ├─ 参数错误（INVALID_* 前缀）──► 读错误消息修正参数，不属故障
          ├─ 运行时错误（NOT_FOUND / QUERY_FAILED / RESTORE_FAILED 前缀）
          │        ├─ 单个资源/子资源 ──► 数据类：该资源确实缺失或不可读（§3）
          │        └─ 大面积失败 ──► 回到环境类或工具缺陷（§4）
          └─ 成功但数据可疑（空/全零/缺属性）──► 数据可信度判定（§3）
```

## 2. 环境类

| 症状 | 检查顺序 | 典型修复 |
|---|---|---|
| 健康字段 `replay_healthy=false` 或带 `replay_error` | 读错误消息；查 RenderDoc 是否弹过设备移除对话框 | 重开捕获；无效则重启 RenderDoc |
| 响应缺健康字段/版本字段 | 三方版本核对（客户端/服务器进程/扩展） | 对齐版本后再测；协议不匹配必须升级 |
| 捕获打不开 | 文件存在性 → 扩展名 → API 支持 → 加载错误消息 | 用捕获列表工具确认路径；换用受支持 API 的捕获验证环境 |
| 所有请求超时/无响应 | 服务器进程是否存活、IPC 目录权限 | 重启 MCP 服务器进程与 RenderDoc |

注意：回放健康是"当前会话"的状态，重开捕获后必须重新核对；不同回放设备（本地/远端）
的计时不可以混算。

## 3. 数据类（成功但可疑）

以下模式来自真实失败案例的通用化，判定时结合当前捕获交叉验证，不生搬硬套：

- **空常量树**：合法空（该槽位确实未绑定/未使用）与异常空（回放占位）表现相同。
  交叉验证：Shader 反汇编是否引用该槽位、其他 action 对同一资源的读取是否正常。
- **导出全零**：清零资源合法；深度/法线等语义数据全零则可疑。用渲染预览、独立再次
  读取、换子资源读取来复核。全零深度不能既不验证就当真值用。
- **网格属性缺失/为空**：区分 VSIn（顶点输入装配问题）与 VSOut/GSOut（输出签名或
  后处理数据问题）。签名/布局类错误有专用错误前缀，此时改读其他阶段或核对管线阶段
  是否真的活跃，不要自行猜偏移解析原始缓冲。
- **颜色域可疑**（导出偏暗/偏亮）：先核对响应的颜色域标注与导出格式的语义，再怀疑
  工具；不同导出格式保留的数值域不同。
- **状态污染**（查询后 UI 事件漂移、替换后结果不变）：记录当前回放位置与替换清单，
  用一个已知查询验证服务端是否恢复；确认污染后，重启会话前的结论要标记存疑。

## 4. 工具缺陷类

判定为疑似工具缺陷的标准：环境健康、数据应当存在、最小请求仍失败或结果与交叉验证
矛盾。此时：

1. 保留最小复现：请求、响应、健康快照、版本四元组。
2. 在报告中标注 `unresolved`，不要基于该数据继续构建。
3. 确需继续任务：如实改用经用户授权的其他来源，并标注来源。

**不要做**：为绕过缺陷猜测内部实现、伪造/插值"看起来合理"的数据、把降级获取的结果
混入纯 MCP 证据链。

## 5. 恢复手段优先级

从轻到重，每步之后都做恢复验证（健康核对 + 已知应成功的最小查询）：

1. 重新定位回放事件 / 重新执行该查询；
2. 重新打开捕获（注意：会使缓存与替换失效，先保存替换清单）；
3. 重启 RenderDoc（扩展会重新加载，版本信息随之重置）；
4. 重启 MCP 服务器进程 / 对齐三方版本。

升级或重装**不是**默认第一步；先把故障归类，再决定是否需要它。
