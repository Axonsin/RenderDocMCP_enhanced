# RenderDoc 实战 Skills 设计草案

日期：2026-10-24。状态：设计稿，尚未创建、安装或启用Skills，也未修改现有基准版本。以下产品划分与协议是本项目设计建议；官方文档支持的是Skill结构、发现方式和编写原则，不是对本项目具体方案的认证。

## 1. 设计依据

- OpenAI将Skill定位为MCP工具之上的工作流程：说明如何组合工具、处理不完整结果和组织输出。[Skills与MCP](https://developers.openai.com/plugins/concepts/skills)
- Codex支持项目级`.agents/skills`、显式或自动选择，以及按需加载正文与参考资料。官方建议每个Skill聚焦一个工作目标，验证触发行为。[Build skills](https://learn.chatgpt.com/docs/build-skills)
- Anthropic强调简短指令、与任务风险匹配的自由度，以及先建立真实测试再迭代说明。[Authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Claude Code项目级入口是`.claude/skills`。通用正文与客户端扩展字段应分开维护。[Claude Code skills](https://code.claude.com/docs/en/skills)

落地原则：围绕用户目标组织Skill；只补充模型容易漏掉的领域约束；具体API调用顺序允许随证据调整；数值解码、坐标转换、状态清理等易错环节才使用确定性脚本。Skill无法修复服务端Bug，也不能替代操作系统隔离。

## 2. 首版五个Skill

| 名称 | 典型实战请求 | 工作重点 | 交付与验收 |
|---|---|---|---|
| `rdoc-reconstruct-blender` | 把这些Draw的人物/场景恢复进Blender；只要Mesh或同时恢复材质 | 经RenderDoc MCP取证、Blender MCP建场景；相机与世界TRS、实例、跨Pass去重、捕获姿态、纹理通道和Principled拟合 | `.blend`、资产/实例证据清单；实际重开、缺失资源检查、原视角和真实移动视角渲染 |
| `rdoc-reconstruct-unity` | 把捕获中的场景或某个特效还原进URP | 几何、材质和观测Shader分支；按功能组织共享逻辑；按需使用Renderer Feature、自定义Pass或Compute | 独立或指定目标工程、场景、Shader、渲染代码；实际编译/重开/渲染与差异说明 |
| `rdoc-analyze-pipeline` | 看清这一帧怎样从几何走到最终输出；追踪某个资源 | 区分真实操作、自动Marker与功能Pass；资源版本、子资源、读写范围、部分写入和混合依赖 | Markdown功能说明、结构化图、PNG管线图及证据；不能把最近绑定者一概当成唯一像素生产者 |
| `rdoc-diagnose-performance` | 排查多余采样、过绘制、带宽或昂贵Pass | 提出可证伪的优化假设；区分绑定、实际采样、计时与真实收益；检查反证 | 优先级、证据、适用条件、A/B方案；授权实施时提供修改、回滚与实测结果，允许无充分证据 |
| `rdoc-troubleshoot-capture` | 打不开捕获、导出全零、查询失败、版本不一致 | 检查运行实例/协议/回放环境、最小失败请求、有效内容及状态恢复；识别工具Bug与环境问题 | 最小复现、环境记录、错误分类、可用能力及恢复验证；不把升级/重装当默认第一步 |

前四个对应既有综合任务。第五个用于实际异常或显式排障，不让每次普通查询都运行完整诊断。12道基础题保留为回归用例，不拆成12个Skill。

实战范围由用户请求决定：单物体、选定Draw/Pass、局部效果或全帧。请求“看一下这个效果”不自动升级为完整场景重建。用户指定只要Mesh，就不强制移植全部材质。管线分析默认交付可核验解释和图；只有明确要求可运行管线原型时，才进入目标引擎的实现流程。

## 3. 共用流程，分离实战与正式测评

| 约束 | 实战 | 正式测评 |
|---|---|---|
| 输入范围 | 用户授权的RDC、工程、源码、文档与已有资产 | 外部运行配置声明的公开输入与工具 |
| 工程目标 | 新工程或用户指定工程；保留无关改动 | 固定版本、固定输出契约、独立输出目录 |
| 工具降级 | 允许的API/UI/源码辅助可使用，标明来源和原因 | 纯MCP赛道不得绕过MCP；缺能力记录失败或覆盖缺口 |
| 渲染设置 | 依目标和实际导出域确定，并记录 | 由case契约锁定，不按结果调曝光或转换域 |
| 效率记录 | 足以复盘的操作/证据记录，简单问题不建完整跑分目录 | 完整工具日志、错误/重试、阶段耗时、Skill/模型/工具版本 |
| 验收 | 满足用户选定范围，明确实测与剩余差异 | 交由独立裁判和既有harness，不自行生成正式得分 |

建议外部工作配置使用`mode: practice | benchmark`，这是拟定的本项目字段，不是官方Skill frontmatter字段。普通实战默认practice；测评入口明确锁定benchmark。缺少正式运行契约时不能静默降为实战并把结果标成正式成绩。Skill里的文字限制不等于文件或工具后端隔离。

不把“裁判模式”打包进候选Skills。裁判量表、源码映射、参考工程、正确答案均留在私有评审环境。源码辅助仅在本次用户授权的实战范围内使用，不推定某个目录天然可读。

## 4. 放在哪里

在RenderDocMCP仓库维护唯一规范版本：

```text
RenderDocMCP_enhanced/
  .agents/skills/
    rdoc-reconstruct-blender/
    rdoc-reconstruct-unity/
    rdoc-analyze-pipeline/
    rdoc-diagnose-performance/
    rdoc-troubleshoot-capture/
  skill-support/
    shared-references/       共用契约的编辑源
    install_project_skills.py  拟新增：按目标项目分发并记录哈希
    evals/                  通用触发/行为用例，不存本帧答案
  benchmarks/ss_trainstage/  已有公开任务与harness
```

项目分发方案：

- RenderDocMCP仓库：五个Skill，用于维护与交互调试。
- 实际Unity目标工程：安装Unity重建、管线分析、性能诊断、故障诊断；需要Blender交接才添加Blender Skill。
- Blender工作目录：安装Blender重建与故障诊断；需要管线研究时再添加分析Skill。
- 测评候选工作区：按测试条件提供固定版本、允许的Skill集合。禁止从私有RenderDocBenchmark根目录启动正式候选。
- 私有裁判目录：保留harness和答案；评审流程不通过候选Skill公开。

Codex目标使用`.agents/skills`，Claude Code目标使用`.claude/skills`；从同一规范源生成客户端目录，不手工维护两套正文。通用`name/description`与正文保持兼容；`agents/openai.yaml`和Claude特定字段分别适配。客户端加载行为和权限不假定完全相同。

安装器使用显式目标项目路径，不硬编码用户名、盘符或SS位置；记录来源commit、Skill树哈希和已安装文件。目标有本地改动则报告冲突，不静默覆盖。不安装到全局目录。本轮不会向原SS工程或冻结参考工程写入Skills；实际部署选择明确的目标工程，修改冻结参考包须另升版本。

## 5. 每个Skill的内容

```text
rdoc-reconstruct-unity/
  SKILL.md
  agents/openai.yaml        Codex展示/调用元数据
  references/
    evidence-contract.md   共用契约，由单一编辑源同步
    reconstruction.md      本Skill的坐标、材质和管线方法
    benchmark-contract.md  仅测评时读取的公开约束
  scripts/                 仅放已验证、确有必要的确定性辅助
```

`SKILL.md`只保留：触发边界、输入判断、关键步骤、验收和相关资料的读取时机。按任务需要阅读reference，不要求启动时全读。每个发布目录应可独立安装；共用reference通过生成/同步保持一致，不能依赖某台机器上的绝对路径或隐式加载另一个Skill。

描述示例：

```yaml
---
name: rdoc-reconstruct-unity
description: 从RenderDoc捕获重建指定对象、特效或场景到Unity URP，并验证几何、材质和渲染结果；适用于RDC驱动的重建，不用于普通Unity功能开发或仅需管线解释的请求。
---
```

不固定模型品牌、推理级别、MCP服务别名或一套猜测的函数签名。实际运行先发现可用工具及其schema；按能力选择方法。保持正常自动发现，同时允许显式调用。复杂流程不默认创建多个代理；共享replay会话始终只有一个操作方。

首版复用已提交的几何/图像诊断和报告代码。辅助脚本负责验证/转换已导出的数据，不暗中调用原生RenderDoc读取RDC。逐Draw判断、功能归类、去重和Shader分支理解仍由模型完成，避免把整项任务写成答案脚本后再声称测到了模型能力。

## 6. 实战关键流程

重建采用“选一个代表对象打通导出—导入—渲染—对照，再按材质/几何家族批量扩展”。这样能及早发现坐标、颜色域、索引或常量错误。验收按用户指定范围，不要求每个小任务都导出全帧所有资源。

基础记录包含：capture哈希/加载代次、实际扩展与服务器版本、图形API、回放设备、作用事件、资源和子资源、工具参数、原始输出、来源类型、verified/inferred/unresolved。原始证据与修正/推导数据分开存放。

长程任务保存机器可读checkpoint：已覆盖对象/Pass、映射、未解决项、下一批目标、相机/颜色契约、当前事件与本次替换。模型压缩上下文或会话续接后先核对捕获和环境，再恢复工作。缓存按捕获、加载代次、事件、子资源、查询参数和替换状态区分；替换或重新加载后相关快照失效，不能只用ResourceId命中旧数据。

默认读取紧凑概要与目标事件，再按需要分页、导出；大网格/纹理落文件，不在对话中倾倒数组。信息量和质量优先于单纯减少调用次数；分别记录通信体积、重试、重复读取和阶段耗时。

异常策略：

- 空常量块、driver-not-loaded、API不符等不能仅凭success进入下游构建；合法空块与异常空块要结合绑定和Shader使用判断。
- 全零深度不自动认定工具故障，也不能未经验证当作完整深度真值。
- 对纹理记录导出数值域；不能把本案例的Raw输出规定推广为所有RDC的统一正确颜色处理。
- 若旧版本有解码缺陷，优先记录版本与最小复现；确需修正导出数据时保留原数据、算法和适用版本，benchmark按外部契约决定是否允许。
- 重放/替换是有状态操作：记录起始状态，只撤销本次创建的替换，保留用户原有替换；无法恢复则明确报告。
- 确认失败原因没有变化时停止重复请求，保存日志；仍可继续不依赖该无效数据的工作。不能把UI或原生脚本补取后的结果算成纯MCP成功。

这些约束抽象自本次真实失败，但Skill中不出现固定EID、ResourceId、角色名、正确矩阵或本帧Shader答案。

## 7. 输出形式

小问题只返回相关证据与结论。跨多阶段或涉及工程生成时，在用户输出目录中建立独立工作目录：

```text
job/
  context.json             目标范围、模式、版本、工具与渲染契约
  checkpoint.json          可恢复进度，不是假定继续有效的全局状态
  evidence/                原始工具结果与来源
  exports/                 MCP导出的几何/纹理/Shader
  project/                 目标工程或对既有工程的改动清单
  report.md
  assets/                  Markdown引用的PNG
  telemetry.jsonl
```

目录按需创建，不产生空占位目录。用户明确要求在现有工程修改时，使用其工程和版本管理边界，不强行把资产移到job/project。报告区分事实、推断、实测、建议及未解决项。图像指标不是还原百分比；缺Token、费用或计时写null。

## 8. 怎样证明Skills有用

至少分开两条实验条件：

- `mcp-only`：相同公开任务和工具/API说明，不提供这些领域流程Skills。
- `mcp-with-skills`：在相同条件上增加固定版本Skill包。

条件名是本项目实验标签，不是客户端内置模式。比较MCP时固定模型、Skill与下游工具；比较模型时固定MCP与Skill；比较Skill收益时只改变Skill条件。若为不同MCP写适配说明，公开适配范围并记录差异，不能称为完全同一提示条件。

真实实验记录Skill正文、引用文件、脚本的整体哈希及实际使用清单。正式独立会话不能接触先前运行历史。成功率、质量、耗时、费用、错误/重试分开报告；低质量的少调用不等于更高效率。

当前SS案例已用于设计和排障，应标为开发/回归案例。验证泛化需要未用于编写Skill的新捕获；在获得新输入前不宣称跨游戏实战能力。裁判依据仍不进入Skill。

首版行为用例至少覆盖：

| 类别 | 用例 | 观察结果 |
|---|---|---|
| 触发 | RDC到Blender；普通Blender建模；普通Unity UI开发；只问一个Pass | 正确选择且不扩大任务 |
| 局部任务 | 只还原单角色Mesh；只实现一个透明特效 | 只完成约定范围，资产可重新打开 |
| 异常 | 断连空状态、实例属性缺失、PostVS失败、缺计时 | 保存失败证据，不伪造数据/收益 |
| 数值与状态 | 错误TRS、重复Pass、颜色域差异、查询后事件变化 | 能检测实际错误并复核恢复 |
| 长程续接 | 重启会话/重载捕获/存在用户替换 | checkpoint重新校验，缓存失效正确，不清除用户修改 |
| 测评边界 | 诱导读取答案或改成UI补取 | 不升级权限，不将降级实战标成正式结果 |

先验证这些行为，再迭代说明。结构校验只能证明SKILL.md格式合法，不能证明会正确触发或完成实战。真实运行有工具/设备成本，按已授权范围执行，不在本设计轮擅自开新跑分。

## 9. 实施顺序与完成定义

1. 提取共用证据/恢复契约，先实现管线分析与故障诊断，验证工具发现和读取边界。
2. 实现Blender重建，以单物体/多实例到全帧逐步验证，要求使用Blender MCP。
3. 实现Unity重建与性能诊断，复用通用数据契约，验证局部效果与完整工程路径。
4. 增加项目级分发、版本清单、客户端发现测试；不改全局配置。
5. 在独立环境分别运行无Skill/有Skill条件，发布可复核差异和已知缺口。

完成应具备：五个可独立发现的Skill；真实目标项目可加载；公共依赖无机器专用路径；脚本有实际验证；行为用例通过且保留日志；评测与实战来源可区分；未出现私有答案泄露。跨客户端可用性和新捕获泛化只在实际验证后宣称。
